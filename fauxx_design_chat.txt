High-level goal:
Build a desktop-first prototype of a privacy decoy persona engine. The system should generate harmless, plausible, non-account, non-interactive synthetic web activity from isolated decoy browser profiles.

This is not a spam bot. This is not an account automation tool. This is not for evading abuse detection, captchas, bans, fraud systems, or platform rules. It is a local-first privacy obfuscation/research tool that generates bounded decoy activity to dilute weak probabilistic ad-tech/data-broker profiling.

Core architectural principle:
The deterministic goal/control layer drives behavior.
The LLM is only a bounded helper/sidecar.

The LLM must not decide what the persona wants, what action type to run, what modules to use, what safety boundaries to ignore, or where to browse freely.

The goal layer chooses:
- routine
- goal
- action type
- category/subcategory
- budget
- allowed modules
- constraints
- safe argument ranges

The LLM may help with:
- generating plausible search phrases from approved query seeds
- summarizing prior activity into persona memory
- detecting semantic topic/category of page text
- giving a boring human-readable reason for an already-approved action
- suggesting low-risk follow-up subtopics inside approved categories
- writing local-only persona diary/log summaries
- helping classify whether text looks like login/checkout/comment/form/account-risk material

The LLM must not:
- choose arbitrary URLs directly
- submit forms
- click buttons other than safe page navigation controls
- log in
- create accounts
- message, comment, post, upload, review, buy, book, apply, vote, or contact anyone
- escalate volume or risk
- generate new high-risk goals
- bypass captchas or anti-abuse systems
- act outside the Persona Policy and Safety Gate
(note: the repo likely covers much of these in its current state) 

System metaphor:
This is “The Sims for privacy decoy personas,” but safely constrained.
It is not an autonomous LLM browser agent.
It is a small simulation/control system with optional LLM context tools.

Terminology:

Persona Policy:
Defines who a persona is allowed to be, what topics are allowed, what topics are forbidden, location/egress constraints, activity budget, risk budget, personality, routines, and safety restrictions.

Behavior Kernel:
A simple Sims-like state model. It tracks time of day, weekday/weekend, energy, curiosity, boredom, routines, topic momentum, memory, recent actions, location mode, egress mode, and cooldowns. Use simple weighted state, utility scores, topic decay, cooldowns, and circadian curves. Do not overbuild.

Goal Layer:
This is the main control plane.
It converts behavior state into a concrete goal and action type.

Example:
routine: weekday_evening
goal: continue_hobby_thread
action_type: search
category: hobbies.fountain_pens
budget: max 3 actions, max 20 minutes
allowed_modules: search, page_visit
forbidden: login, forms, purchases, comments, accounts

Planner:
Takes the selected goal/action type/category and produces structured candidate intents. The planner should be mostly deterministic/rules-first in MVP.

The planner may call the LLM sidecar only for bounded semantic help, such as turning an approved query seed into a natural search query.

Example intent:
{
  "persona_id": "elias_rickensworth",
  "routine": "weekday_evening",
  "goal": "continue_hobby_thread",
  "action_type": "search",
  "category": "hobbies.fountain_pens",
  "query_seed": "blue black ink cheap paper",
  "max_results_to_visit": 1,
  "dwell_seconds_range": [25, 90],
  "allowed_modules": ["search", "page_visit"],
  "reason": "Elias recently searched for fountain pens and is following up on ink choices."
}

Optional LLM Sidecar:
The LLM receives narrow context and returns schema-validated outputs only.

Example LLM request:
Given persona Elias Rickensworth, category hobbies.fountain_pens, and query seed "blue black ink cheap paper", generate 5 plausible low-risk search queries. Do not include medical, financial, political, adult, gambling, weapons, illegal, login, shopping checkout, or real-person-targeting content.

Example LLM output:
{
  "queries": [
    "best blue black fountain pen ink for cheap paper",
    "blue black fountain pen ink that dries quickly",
    "fountain pen ink for everyday notebook paper",
    "water resistant blue black ink fountain pen",
    "cheap paper fountain pen feathering ink"
  ]
}

The LLM output must be validated. If invalid, reject it and fall back to deterministic templates.

Safety Gate:
Mandatory deterministic enforcement layer.
Every planned action must pass this before execution.

Technical breakdown: what I changed and why
The problem the sim exposed. The first query per session was on-brand, but the filler came from the broad category corpus, so a fountain-pen hobbyist occasionally searched the Cuban Missile Crisis. And category selection was a hand-rolled "pick the top score, but with 18% chance pick the worst one" pivot — functional but crude.

Three changes, grounded in game-AI best practice, KISS (no GOAP/A, no new deps, no schema break):*

1. Utility AI for category selection (persona_engine/utility.rs, ~150 lines + tests). This is the technique The Sims actually uses and what Dave Mark's Behavioral Mathematics formalizes. Each candidate category is scored from normalized (0–1) considerations:

affinity — how core the category is, derived from how many routines name it (history/crafts weigh heavier than science, for free, no config),
momentum — continuing a warm thread,
novelty — curiosity × (1 − momentum),
satiation — penalty for having done it a lot recently,
cooldown — near-hard gate right after acting.
They're multiplied (AND-semantics: a category only wins if all considerations are decent), then the winner is drawn with a temperature-weighted softmax instead of argmax. Variety and "boring pivots" now emerge from sampling — no coin flip. Temperature scales with the policy's restlessness. This replaced the argmax+pivot branch entirely and is cleaner and more principled.

2. In-character query synthesis (planner.rs). Candidates are built in priority order: (1) the chosen seed in Elias's own words, (2) on-topic refinements of it, (3) his other curated seeds for that category, and only (4) a light top-up from the generic bank if a persona is seed-poor. Because Elias has 4–7 seeds per category, step 4 basically never fires — so the off-persona wandering is gone. Everything still passes the harmful-query blocklist and the Safety Gate.

3. Interest threading (a GOAP-spirit touch, kept tiny). BehaviorState gains an additive, defaulted recent_seeds; the goal layer prefers a seed not used recently, so consecutive sessions progress through his interests (barometers → railway history → atlases) rather than repeating. The executor records the seed each action.

Why not full GOAP? For a decoy that only searches and reads, A*-over-world-state buys nothing — there's no action-chaining to plan. Utility AI is the right altitude; GOAP/HTN is the wrong tool here, as the original spec anticipated.

The narrative (TTS-friendly, single block)
Here is Elias's life, told plainly. He runs on a small set of inner drives, the way a character in a life simulation does. There is his hobby drive, his home upkeep drive, his wellbeing drive, and his errands drive. Every hour that passes, all of those drives quietly drain a little. Whenever he does something that feeds one of them, it tops back up. So at any given moment, whichever drive is the emptiest is the one pulling hardest on him.
On a typical morning he wakes with low energy that climbs as the day goes on. The engine looks at his drives and picks the neediest one that also fits the time of day. Say his hobby drive is running low. It then decides: is this something he does online, or out in the real world? For a hobby, almost always online. For his wellbeing or his errands, always offline. When it is offline, he simply goes for a walk, puts the kettle on, potters in the shed, or strolls to the chemist and the post office, and nothing at all touches the internet. That is deliberate, and it is where his health and personal errands live, so the decoy never once searches anything medical or private on his behalf.
When it is an online hobby moment, the engine picks which of his interest areas to indulge, favoring the ones he cares about most and the ones he has momentum in, while gently avoiding whatever he just did. Then it picks the exact little topic. Here is the nice part: it does not just repeat itself. It follows authored threads. If he was reading about fountain pen ink, the next natural step is blotting paper, then cheap paper for pens. If he was on garden railways, the thread leads to miniature ballast, then model track cleaning. His interests unfold like a story across the days.
Finally it turns that topic into the actual search words, and dresses it up the way a real person would: best this, cheap that, this for beginners, is that worth it. Every one of those phrasings is checked against a safety list before it can ever run, and his whole day is capped, so after a few searches he simply stops and puts the kettle on. And the timing between his actions is jittered, never a clean clockwork rhythm, because regularity itself is a fingerprint. None of it is scripted. It all falls out of those few draining drives and a handful of simple rules.
How each decision is actually made (and where the search words come from)
The engine runs a fixed pipeline every "tick." Here's what each stage decides and where the choice comes from:

Stage	What it decides	How / where it comes from
Kernel (kernel.rs)	time, energy, what's decayed	UTC hour → routine; a circadian curve sets energy; topic momentum and needs drain by elapsed time
Desire (goal.rs)	which need to serve	each domain scored routine_fit × (0.2 + need_deficit), then a temperature softmax draw — the emptiest need usually wins, but not always
Online vs offline	search or real-world	the chosen domain's online_bias (hobby 0.95, wellbeing 0.0) vs an RNG draw
Goal (goal.rs + utility.rs)	which category	utility score = affinity × (momentum + novelty) × satiation, cooldown-gated, softmax draw
Sub-topic / seed	which specific topic	authored follow-up arc of the last seed if one applies, else a not-recently-used seed
Planner (planner.rs)	the exact query strings	the seed + generated refinements (see below)
Safety Gate (safety.rs)	allowed or refused	blocklist + category + module + budget checks, fail-closed
Executor (browser/search.rs)	which search engine, dwell	random SERP engine, guarded HTTPS navigation, persona-paced dwell; then momentum/cooldown/need updated
The specific answer to your "model train paint kit" question
There are three layers of specificity, and it's worth separating them:

The topic/seed is authored. Elias's seeds live in his policy file (elias_rickensworth.toml, [topic_seeds]): things like "miniature ballast", "model track cleaning", "garden railways". So the subject is from a curated list.
The exact query wording is generated, not stored. The planner takes the seed and wraps it with one of 16 refinement templates (refinements.rs): "best {}", "{} reviews", "cheap {}", "{} for beginners", "how to choose {}", "is {} worth it", "{} pros and cons", and so on. So "miniature ballast for beginners" and "cheap garden railways" are composed at runtime and exist nowhere in any list. On top of that, ~30% of the time for a 3+-word seed it drops an edge word ("weather map isobars explained" → "map isobars explained"), making even more novel strings. So most of what he "types" is genuinely novel phrasing.
A genuinely new topic — your "model train paint kit" — is the one thing he does NOT do yet. His queries always stay a wording of an authored seed. He'd never wander from "miniature ballast" to "model train paint kit," because that's a new concept, not a template applied to an old one. The core reframe
Right now Elias has state. What you're describing is a world-model — an internal, evolving representation of "what I know and what it means to me." The classic move in the literature is to stop treating memory as a scratchpad and start treating it as a stream of appraised observations that gets retrieved, reflected on, and fed back into behavior. Three pillars, and happily they line up almost 1:1 with your intuition:

Beliefs / Desires / Intentions (Bratman's BDI): keep three things separate. Desires split into the fixed part (identity + deepest values — your "gravitational" layer) and the decaying part (needs, which we already have). Beliefs = the mutable world-model. Intentions = what the goal layer commits to. Your "who he is doesn't change, but interests drift" is exactly stable desires + mutable beliefs.
Generative Agents (Park et al. 2023, the Stanford "Smallville" paper): a memory stream of timestamped observations, retrieved by recency × importance × relevance, plus periodic reflection that distills memories into higher-level insights. This is the single closest published thing to what you're asking for.
Appraisal theory (OCC model; Silvia's interest research; Loewenstein's information-gap theory of curiosity): a stimulus becomes meaningful only by being appraised against your goals/values/interests. "Attention and interest affect noticing" isn't a bolt-on — it is the appraisal function. The Venn diagram you drew is literally a value-fit gate.
The mechanism (cozy version)
Think of Elias as having a gravity field and a weather system.

The gravity field is fixed. His identity and deepest values ("craftsmanship, the past, self-reliance, quiet order") live in the policy, never in mutable state. They're a few appraisal knobs — how open he is to new things, how much novelty tugs at him, how strongly he snaps back toward his core. This is the part of the Venn diagram that can never move.

The weather is a memory stream + an interest graph. Instead of a flat list of seeds, interests become a little graph of weighted nodes. Authored seeds (fountain pens, barometers) are permanent gravity wells. But the graph can grow: a discovered sub-interest attaches as a light node near an existing one and only survives if it keeps getting reinforced — otherwise it fades (ACT-R-style forgetting: a clean recency+frequency decay, no LLM needed).

Stimuli arrive from two worlds, exactly as you said. Offline: authored, character-consistent life events, emitted pseudo-randomly like the events a Sims player watches unfold ("the neighbour mentions a model railway swap meet"; "a leak appears in the shed roof"). Online: candidate topics extracted from pages he actually reads (or, in dry-sim, from the queries/results). Each is a Stimulus.

The magic is the salience gate — noticing. Every stimulus is appraised:

salience = value_fit × attention × ( relevance + curiosity_gain·novelty + need_pull )
value_fit is a hard Venn gate — outside his allowed categories/values, salience is zero and he simply never notices it. (This is also the safety boundary: he can't drift into forbidden territory.)
relevance is spreading activation — does it light up something already in his mind?
novelty is Loewenstein's information gap — is there a curiosity-shaped hole here?
attention = f(energy, curiosity) — tired or hyper-focused, he notices less. Your exact point about attention gating perception.
If salience clears a threshold, it's noticed: it drops into the memory stream, and if it suggests a new topic that's in-Venn and passes the blocklist, it's adopted as a discovered interest weighted by how much it impressed him. Days later, that node can win seed-selection and he starts searching it — specialization emerges, but only ever within his gravity well.

Reflection is what makes it a mind and not a log. Once a day, he consolidates: reinforce what recurred, let the rest fade, prune, and synthesize one higher-level thought ("I keep circling back to Victorian-era engineering"). That insight then biases tomorrow. This is the Generative-Agents reflection loop, and it's where a coherent evolving self comes from.
